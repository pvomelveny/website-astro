# Patrick O'Melveny — Personal Website

Personal academic website built with [Astro](https://astro.build), with the notes
section generated by [wanshi](https://github.com/pvomelveny/wanshi) from Typst
sources. Deployed as a static site on AWS S3 + CloudFront.

## Prerequisites

Node ≥ 22.12, plus two tools for the notes:

```sh
brew install typst                       # wanshi compiles every note with it
cargo install --git https://github.com/pvomelveny/wanshi
```

## What is where

```
src/
  data/
    site.ts          ← Global personal info: name, email, GitHub, Scholar, CV URL
    research.ts      ← All publications and talks (papers, preprints, talks arrays)
    teaching.ts      ← Teaching history (currentCourse, pastCourses)

    notes.ts         ← Reads wanshi.json — the bridge from the notes to Astro

  pages/
    index.astro      ← Landing page — bio, research interests, recent notes
    about.astro      ← About page — personal statement, research interests, CV link
    research.astro   ← Research page — reads from src/data/research.ts
    teaching.astro   ← Teaching page
    rss.xml.ts       ← RSS feed — built from the notes metadata index

  components/
    BaseLayout.astro ← HTML shell: fonts, KaTeX CSS, meta tags
    Nav.astro        ← Top navigation bar (reads name from site.ts)
    Footer.astro     ← Footer with email/GitHub/Scholar links (reads from site.ts)
    Paper.astro      ← Single paper/preprint entry with abstract toggle
    Talk.astro       ← Single talk entry

  scripts/
    abstracts.ts     ← Client-side: toggles abstract open/closed on research page

  styles/
    global.css       ← CSS custom properties (color tokens, font variables, layout)

  types/
    note.ts          ← TypeScript types for notes + URL helper
    research.ts      ← TypeScript interfaces for papers, preprints, talks
    teaching.ts      ← TypeScript interface for teaching entries

scripts/
  gen-wanshi-chrome.ts ← Generates the nav/footer/meta wanshi injects, from site.ts

notes/               ← The wanshi project — everything under /notes/
  Wanshi.toml        ← wanshi configuration (annotated)
  trees/             ← Typst sources; one .typ per note, path = URL slug
    index.typ        ← Forest root, published at /notes/ — lists notes automatically
    _lib/wanshi.typ  ← Bundled Typst library (synced by `wanshi upgrade`)
  assets/            ← Copied to /notes/assets/; favicon.ico symlinks public/
  import-*.html      ← Hooks splicing site chrome into every generated page

public/              ← Static assets served as-is: photo.jpg, cv.pdf, favicon
  notes/             ← GENERATED by wanshi, gitignored — never edit
```

### How the two generators fit together

Astro owns `/`, `/about`, `/research`, `/teaching` and `/rss.xml`; wanshi owns
everything under `/notes/`. wanshi writes complete standalone HTML into
`public/notes/`, and Astro copies `public/` into `dist/` untouched — so the
deploy is still a single `dist/` upload.

They connect in two directions:

- **Astro → wanshi:** `scripts/gen-wanshi-chrome.ts` generates the site nav and
  footer from `src/data/site.ts` into `notes/import-*.html`, which wanshi
  splices into every notes page. Edit `site.ts`, not the generated HTML.
- **wanshi → Astro:** wanshi writes `wanshi.json`, a metadata index, which
  `src/data/notes.ts` reads to build the homepage's "recent notes" list, the RSS
  feed, and the notes' entries in the sitemap.

Because Astro reads a file wanshi produces, **wanshi has to run first** —
`npm run build` does this for you.

## Common tasks

### Update personal info

Edit **`src/data/site.ts`** — name, email, GitHub, Google Scholar URL, CV path. This file is imported by Nav and Footer so a change here propagates everywhere.

### Update page content (bio, research statement, etc.)

Each page has a `// ── Page content ──` block near the top of its `---` frontmatter. Everything inside that block is a plain `const` — edit the strings directly.

### Update the teaching page

All teaching data lives in **`src/data/teaching.ts`**.

**Current course** — set `currentCourse` to an object, or `null` when not teaching:

```ts
export const currentCourse: TeachingEntry | null = {
  title: 'Math 308 — Matrix Algebra',
  term: 'Spring 2026',
  role: 'TA',                   // 'TA' or 'Instructor'
  institution: 'University of Washington',
  url: 'https://canvas.uw.edu/courses/...',  // optional — omit if no link
};
```

When `url` is set the Canvas note renders as a link; without it, plain text. Edit `currentClassNote` to change the message.

**Past courses** — append to `pastCourses` in any order; the list sorts automatically:

```ts
export const pastCourses: TeachingEntry[] = [
  {
    title: 'Math 407 — Linear Programming',
    term: 'Fall 2025',
    role: 'TA',
    institution: 'University of Washington',
  },
  {
    title: 'Math 308 — Matrix Algebra',
    term: 'Spring 2025',
    role: 'TA',
    institution: 'University of Washington',
  },
];
```

Sorting is derived automatically from the `term` string. Order within a year: Winter → Spring → Summer → Fall.

### Add a publication or talk

Open **`src/data/research.ts`** and append an object to `papers`, `preprints`, `talks`, or `additionalWriting`. The page re-renders automatically on the next build — no HTML changes needed. Field definitions live in `src/types/research.ts`.

`coauthors` is **collaborators only** — omit yourself. Each entry is an object: `{ name, url? }`. When a `url` is given the name renders as a link.

Optional fields can be omitted entirely. The full file shape with one entry in each list:

```ts
const research: ResearchData = {
  papers: [
    {
      title: "Facets of the spanning tree polytope",
      coauthors: [
        { name: "Jane Smith", url: "https://jsmith.example/" },
        { name: "Alex Lee" },           // url is optional
      ],
      year: 2025,
      venue: "Journal of Combinatorial Theory, Series B",
      volume: 168,                      // optional
      pages: "214–239",                 // optional — use an en-dash, not a hyphen
      tags: ["polyhedral combinatorics", "network design"],
      links: {
        journal: "https://doi.org/...",
        pdf: "/papers/spanning-tree.pdf",      // optional
        arxiv: "https://arxiv.org/abs/...",    // optional; only when also published
      },
      abstract: "We characterize a new family of facet-defining inequalities...",
    },
  ],

  preprints: [
    {
      title: "On the integrality gap of the subtour LP",
      coauthors: [{ name: "Jane Smith" }],
      year: 2025,
      tags: ["combinatorial optimization", "TSP"],
      links: {
        arxiv: "https://arxiv.org/abs/...",
        pdf: "/papers/subtour-gap.pdf",        // optional
      },
      abstract: "We construct a new family of TSP instances...",
    },
  ],

  talks: [
    {
      title: "Polyhedral methods in combinatorial optimization",
      venue: "SIAM Conference on Optimization",   // optional
      year: 2025,
      month: 5,                                   // 1–12 (numeric)
      links: {
        slides: "/slides/siam-opt-2025.pdf",      // optional
      },
    },
  ],

  additionalWriting: [
    {
      title: "A short note on something",
      subtitle: "M.A. Thesis, San Francisco State University",
      year: 2023,
      coauthors: [{ name: "Jane Smith" }],       // optional
      links: {
        pdf: "/writing/note.pdf",                // optional
        link: "https://example.org/catalog/...", // optional, generic link
      },
      abstract: "Optional abstract text...",
    },
  ],
};
```

Talks sort newest-first automatically using `year` + `month`. arXiv links on published `papers` are conventionally included only when the paper also appears elsewhere; pure preprints belong in the `preprints` array and use arXiv as the primary link.

### Write a note

Notes are Typst files under `notes/trees/`, built by wanshi. Scaffold one:

```sh
npm run notes:new -- matching-polytope
```

That writes `notes/trees/matching-polytope.typ`, published at
`/notes/matching-polytope.html`. **The path under `trees/` is the slug**, so
`npm run notes:new -- polytopes/matching` gives `/notes/polytopes/matching.html`.
Renaming a file changes its URL and breaks inbound links — pick a name you can
live with.

Complete minimal file:

```typst
#import "/_lib/wanshi.typ": *

#show: wanshi

#metadata((
  "title": "Why is the matching polytope half-integral?",
  "taxon": "exposition",
  "date": "2026-06-01",
  "description": "A look at what LP relaxations know about matchings.",
))

The matching polytope is the convex hull of all incidence vectors of matchings
in a graph $G = (V, E)$.#footnote[
  For a full treatment see Schrijver, _Combinatorial Optimization_, ch. 24–25.
]
Understanding its facet structure is central to polyhedral combinatorics, and
it builds on #local("/polytopes/basics").

The natural LP relaxation is defined by

$ x_e >= 0 quad forall e in E, quad sum_(e in.rev v) x_e <= 1 quad forall v in V $

Every vertex of this polytope is half-integral.
```

**Metadata fields:**
- `title` — may be rich Typst content, not just a string
- `taxon` — the note kind; keep to `note` · `exposition` · `problem` · `reading`
- `date` — `YYYY-MM-DD` sorts most reliably; set it on everything, or the note sorts last in the feed
- `description` — one sentence; shown on the homepage list, in the RSS feed, and in the page's metadata row

**Math** is Typst syntax, not LaTeX — `$x$` inline, `$ x $` (with spaces) for
display. It renders as MathML, so there is no KaTeX and no CDN request. Note
that a note is *not* findable by search on a symbol it contains; search for the
words around a formula.

**Linking** is the substance of the system. `#local("/some/slug")` links another
note, and backlinks are generated automatically — so every link you write pays
for itself twice. Add at least one link in each direction before considering a
note done.

**Footnotes** are Typst's `#footnote[...]`, rendered at the end of the note.
(The margin sidenotes the old MDX notes had have no wanshi equivalent.)

**Diagrams** from packages like `fletcher` or `cetz` must be wrapped to survive
the HTML export: `#auto-figure(auto-frame(...))`.

**The index page maintains itself.** `notes/trees/index.typ` calls `#children()`,
which lists every note automatically — you never edit it to add one.

Full documentation is in the [wanshi repo](https://github.com/pvomelveny/wanshi)
under `docs/users/` — start with `writing-notes.md` and `links-and-references.md`.

## Development

```sh
npm run dev      # build notes once, then start the dev server at localhost:4321
npm run build    # production build → dist/
npm run preview  # serve the dist/ build locally to check before deploying
```

`astro dev` only watches Astro sources, so `npm run dev` builds the notes once
and does not re-run wanshi when a `.typ` file changes. **To write notes, run a
watcher in a second terminal:**

```sh
npm run notes:watch   # rebuilds notes/ into public/notes/ on every save
```

Both terminals feed the same `localhost:4321`. Other notes commands:

```sh
npm run notes:check   # validate the graph — dangling links, duplicate slugs, Typst errors
npm run notes:build   # build the notes only
npm run notes:chrome  # regenerate the injected nav/footer from src/data/site.ts
```

`npm run build` runs `notes:check` in strict mode, so a dangling link fails the
build. The production build is fully static — just files in `dist/`.

> **Note:** wanshi resolves some paths relative to the working directory, so it
> must be run from inside `notes/`. The npm scripts handle this; if you invoke
> it by hand, `cd notes` first rather than passing `--config`.

## Deployment (AWS)

> **Status:** The infrastructure below still needs to be created. This section describes the intended workflow once the S3 bucket and CloudFront distribution exist.

### One-time setup (to do)

1. Create an S3 bucket (e.g. `pvomelveny-website`) with static website hosting **disabled** — CloudFront will serve the files directly, not S3.
2. Create a CloudFront distribution pointing at the S3 bucket. Use an Origin Access Control (OAC) so the bucket stays private and only CloudFront can read from it.
3. Attach a TLS certificate via ACM for the custom domain.
4. Create an IAM user or role with `s3:PutObject` + `s3:DeleteObject` on the bucket and `cloudfront:CreateInvalidation` on the distribution. Store the credentials as GitHub Actions secrets: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `S3_BUCKET`, `CLOUDFRONT_DISTRIBUTION_ID`.
5. **Attach a CloudFront Function** (viewer request) that rewrites directory URLs
   to `index.html`. With static website hosting disabled, CloudFront asks S3 for
   the literal key, so `/about` and `/notes/` would 404 without it — Astro emits
   `about/index.html`, and the notes forest root is `notes/index.html`:

   The two generators shape URLs differently, so the rewrite branches on the
   `/notes/` prefix. Astro publishes a page as a **directory**
   (`about/index.html`, served at `/about`); wanshi publishes a note as a **flat
   file** (`welcome.html`) but links it without the suffix, because
   `pretty-urls` is on. Directory indexes inside the forest keep a trailing
   slash and behave like Astro's.

   ```js
   // CloudFront Function, event type: viewer request.
   // Written to ES5 so it runs on either CloudFront Functions runtime.
   function handler(event) {
     var request = event.request;
     var uri = request.uri;

     // Directory URLs: "/", "/about/", "/notes/", "/notes/algebra/".
     if (uri.charAt(uri.length - 1) === '/') {
       request.uri = uri + 'index.html';
       return request;
     }

     // A dot in the last segment means a real file — "/notes/welcome.html",
     // "/notes/main.css", "/cv.pdf", "/_astro/x.webp". Pass it straight
     // through. Only the last segment is tested, so a directory containing a
     // dot does not disable the rewrite.
     var last = uri.substring(uri.lastIndexOf('/') + 1);
     if (last.indexOf('.') !== -1) {
       return request;
     }

     // "/notes/welcome" → "/notes/welcome.html"   (wanshi: flat files)
     // "/about"         → "/about/index.html"     (Astro: directories)
     if (uri.lastIndexOf('/notes/', 0) === 0) {
       request.uri = uri + '.html';
     } else {
       request.uri = uri + '/index.html';
     }

     return request;
   }
   ```

   Because wanshi still writes `.html` files on disk, `/notes/welcome.html`
   keeps working alongside `/notes/welcome` — turning `pretty-urls` on does not
   break any link already published.

   The same rewrite is implemented for the dev server as a Vite plugin in
   `astro.config.ts` (`notesDevUrls`), since Astro's dev server serves `public/`
   by exact path only. **Keep the two in step.**

   One thing to avoid: a note whose *filename* contains a dot (`v1.2.typ`)
   produces `/notes/v1.2`, which this function reads as a file and passes
   through unrewritten. Keep dots out of note filenames.

6. **Add custom error responses.** With OAC and a bucket policy granting only
   `s3:GetObject`, S3 answers a missing key with **403**, not 404 — it will not
   confirm whether the object exists. Map both `403` and `404` to your error
   page with an HTTP 404 response code, or every typo'd URL shows an AWS access
   denied page. This site has no error page yet; add `src/pages/404.astro` first.

### Manual deploy (once setup is done)

```sh
npm run build
aws s3 sync dist/ s3://YOUR-BUCKET-NAME --delete
aws cloudfront create-invalidation \
  --distribution-id YOUR-DISTRIBUTION-ID \
  --paths "/*"
```

`--delete` removes stale files from S3. The CloudFront invalidation flushes the CDN cache so visitors see the new version immediately (free up to 1,000 path invalidations/month).

### Automated deploy via GitHub Actions (to do)

Create `.github/workflows/deploy.yml` — runs on every push to `main`:

```yaml
name: Deploy

on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      # The notes are built by wanshi from Typst sources, so CI needs both.
      # Neither is an npm dependency. `cargo install --git` is slow (a few
      # minutes) and worth caching, or replacing with a prebuilt binary.
      - uses: typst-community/setup-typst@v4
      - uses: actions/cache@v4
        with:
          path: ~/.cargo/bin/wanshi
          key: wanshi-${{ runner.os }}
      - run: |
          command -v wanshi >/dev/null \
            || cargo install --git https://github.com/pvomelveny/wanshi

      - run: npm ci
      - run: npm run build
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: us-east-1
      - run: aws s3 sync dist/ s3://${{ secrets.S3_BUCKET }} --delete
      - run: |
          aws cloudfront create-invalidation \
            --distribution-id ${{ secrets.CLOUDFRONT_DISTRIBUTION_ID }} \
            --paths "/*"
```

With this in place, pushing to `main` builds and deploys the site automatically with no manual steps.
